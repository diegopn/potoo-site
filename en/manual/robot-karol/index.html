01 · overview

What is Robot Karol

Robot Karol teaches programming through actions performed by a robot in a grid world. Rather than starting with an empty screen and many abstract concepts, students can observe movement, orientation, and obstacles after each command.

The current online project keeps this teaching focus and offers tasks, a visual representation, and block or text editing. Materials may provide different code forms and levels; use the documentation that matches the activity.

Status in Potoo IDE: Robot Karol is under evaluation. It is separate from Karel the Robot; no integration with the app is available.

02 · execution world

The grid world

The robot occupies a cell and has an orientation. A task’s scenario defines the space, obstacles, and, where relevant, marks or goals. A command changes the world state: the robot moves, turns, or interacts with available elements.

ComponentRole in an exercise
RobotExecutes instructions and keeps position and direction.
GridDefines the positions through which the robot can move.
ObstaclesRestrict movement and motivate sensor use.
Marks or objectsMay represent elements the robot encounters or changes.
Goal scenarioDescribes the state the solution must reach.

Read the initial conditions before programming. The same algorithm can fail if the starting direction or obstacle position changes.

03 · actions

Commands and sensors

Basic actions change the robot’s position or orientation. Conditions inspect the surroundings so a program can respond to its scenario. In the native text mode, a sequence can use German commands:

Schritt
LinksDrehen

The snippet moves forward one cell and turns left. These commands also correspond to blocks in the visual editor; Python and Java modes are separate teaching materials.

  • Actions: move, turn, and interact with objects defined by a task.
  • Conditions: check a clear path, obstacles, or objects in the current cell.
  • Observation: inspect world state before deciding what to do next.

Text-mode vocabulary

The project documents commands in German. They appear in its own text mode and correspond to blocks in the visual editor. The repository summarizes the main instructions as follows:

CommandDocumented effect
Schritt / Schritt(anzahl)Moves forward one cell or the specified number of cells.
LinksDrehen / RechtsDrehenTurns 90 degrees left or right; text mode accepts an optional count.
Hinlegen / Hinlegen(anzahl)Places one brick or the specified number in front.
Aufheben / Aufheben(anzahl)Picks up one brick or the specified number in front.
MarkeSetzen / MarkeLöschenMarks the current cell or removes its mark.
BeendenStops the program at that point.

These names belong to Robot Karol's own notation and keep their German spelling. By contrast, karol.schritt() is a Python call shown in the associated course. They are different syntaxes; check which code mode is active before copying an example.

04 · control flow

Sequence, loops, and conditions

The environment teaches programs built from sequences, repetitions, and conditional choices. Some materials include repetition a fixed number of times and repetition controlled by a sensor.

IdeaUseful question
SequenceWhich action should happen first?
Counted repetitionHow many steps or turns are needed?
Conditional repetitionWhich sensor says to continue or stop?
DecisionWhat should happen when the path is clear or blocked?
ProcedureWhich sequence should have a name so it can be reused?

Sensor-based conditions make an algorithm adaptable to related scenarios. Still, test every case specified by the exercise and ensure that a loop can finish.

Text forms for repetition and decisions

The repository documents counted repetition, condition-based repetition, continuous repetition, and one-way or two-way decisions. In text mode, dedicated words delimit each block:

wiederhole 4 mal
  Schritt
endewiederhole

wenn IstWand dann
  LinksDrehen
sonst
  Schritt
endewenn

Use counted repetition when the number of actions is known. Use a condition when the task depends on the world, such as continuing until the robot finds a wall. An infinite loop needs a clear way to stop, such as an explicit stop command or an external condition.

Sensors and decisions

Text mode includes questions about walls, bricks, marks, and the robot's orientation. Affirmative and negative forms are available, and some questions accept an expected brick count. Before combining sensors, determine whether a question refers to the current cell, the cell ahead, or an absolute direction; that distinction changes the program's decision.

05 · editing modes

Blocks, text, and activities

The online project offers visual block editing and text editing. Blocks make loop and condition structure visible; text helps students study commands and can prepare them to move into programming languages.

The platform also organizes tasks and course material. In a lesson sequence:

  1. read the goal and inspect the world’s initial state;
  2. write a strategy before placing blocks;
  3. run the program and observe where the robot diverges from the goal;
  4. change the smallest necessary part and test again.

Some courses accompany the activities with Python or Java. Those modes are specific teaching materials and should not be confused with Robot Karol’s own representation.

Reusable instructions and editor flow

A custom instruction names a group of commands so it can be reused in different parts of a solution. The repository documents definitions delimited by Anweisung and endeAnweisung. This makes it easier to name operations such as crossing a corridor, building one side, or returning to the starting point.

When a task contains several blocks, the block designated as the main program is the one that runs. Helper blocks remain inactive until called. In text mode, a continuous program can run without a visual block structure. The documentation also describes comments with // and older asterisk forms; follow the syntax used in the course material.

The task editor lets a teacher create custom worlds and goals, then share them as a link or file. A useful activity states the starting position and direction, obstacles, available objects, and expected final state.

06 · worked example

Traverse a clear row

Suppose a task asks the robot to move along a corridor of known length. In the native text mode, the documented repeat form can run the forward command four times; in the block editor, use the equivalent block.

wiederhole 4 mal
    Schritt
endewiederhole

Equivalent block structure:

  • Hauptprogramm
    • wiederhole 4 mal
      • Schritt

Expected result: in a corridor with four clear cells ahead, the robot moves forward four cells and keeps its heading. If the route may be shorter or contain obstacles, check it with a sensor before choosing how many steps to run.

Progressive exercises

Try these tasks in Robot Karol’s own text mode or with the equivalent blocks. For each stage, write down the initial state, the goal state, and a test that proves the solution before generalizing it:

StageTaskCheckpoint
1 · sequenceMove along an empty corridor of fixed length.Check the count and orientation after the last step.
2 · repetitionBuild a square from bricks or walk its four sides.Compare position, direction, and objects with the starting state.
3 · decisionTurn or move depending on whether a wall is ahead.Run one clear scenario and one blocked scenario.
4 · procedureName a compound action and reuse it in another part of the route.Change one helper instruction and check all its call sites.
5 · generalizationRepeat the task in a custom world with a different starting position.Separate assumptions guaranteed by the prompt from those needing sensors.

07 · planning

Plan and debug tasks

Robot tasks are useful decomposition exercises. Name repeated actions, identify sensor-based choices, and sketch the route on a grid. Visual execution helps locate the step where orientation or position became unexpected.

  • Test the exact initial scenario from the exercise.
  • Watch orientation after every turn.
  • Check whether sensors are relative to the robot’s current direction.
  • Test boundary cases, such as the shortest corridor and an obstacle immediately ahead.
  • If a solution uses Python or Java, check the integration semantics in the accompanying material.

The goal is a sequence that works under the exercise conditions, not only in the first scenario you tried.

Test cases for a grid world

A task may appear solved in one world and fail when the distance or starting position changes. Separate the algorithm from the concrete setup: write down its assumptions and check that the task guarantees them.

  • Test the shortest valid corridor and the longest one allowed by the task.
  • Place a wall immediately ahead to check the sensor response.
  • Test both sides of every decision, including a missing mark or brick.
  • After a turn, confirm orientation before interpreting a directional question.
  • Run the task again after changing the order of a helper instruction's commands.

When the robot stops short of the goal, compare its state after each command: cell, orientation, and changed objects. This trace often shows whether the error is in the route, a repetition boundary, or the stopping condition.

08 · related projects

Robot Karol and Karel the Robot

Robot Karol and Karel the Robot share the educational idea of controlling a robot, but they are different projects and ecosystems. The Karel reference on this site follows a Stanford Java model; Robot Karol has its own German environment, online platform, and teaching materials.

Commands, sensors, syntax, and behavior are not interchangeable. Code written for one Karel implementation should not be presented as Robot Karol code without adaptation and testing.

09 · versions and scope

Versions and support

The block and text examples in this section follow Robot Karol Online v1.10.13 and that release’s README; the live platform may include later changes. The Python and Java courses are separate teaching modes, not Robot Karol’s native block and text language.

The manual describes the original environment. It does not mean Potoo IDE includes the simulator, robot, or tools from the project. Robot Karol remains under evaluation.
