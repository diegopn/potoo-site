01 · overview

What is Kalimat

Kalimat (كلمات, “words”) is a language that lets learners program using Arabic vocabulary and writing. The official website presents it as an option for beginners and describes its own tools and documentation. It is a language project, not merely a translation of keywords from another language.

The language of code is part of the learning experience; familiarity with the alphabet and writing direction should be considered when preparing materials and examples.

Status in Potoo IDE: Kalimat is under evaluation and is not run by the app. Check the official portal for current releases and rules.

02 · audience and goals

Who it was designed for

The project describes Kalimat as a language for beginners, including children. Arabic syntax aims to bring written code closer to a learner’s language, while libraries and language features allow programs beyond console exercises.

When studying Kalimat, separate three parts:

  • the language and its writing rules;
  • the tools needed to edit and run programs;
  • libraries that provide graphics or integration with other languages.

Availability of each component may depend on the distribution being used. Guides in the official package are the source for installing and running a current version.

Language, tool, and library are separate layers

The project presents Arabic as part of making an early programming experience accessible: learners can connect names and instructions to a language they already read and use. That does not remove the need to learn ideas such as state, decisions, and repetition; it changes the vocabulary used to introduce them.

Separate study into three layers. First, find the language rules in the distributed guide. Then learn to use the environment that edits and runs a program. Finally, consult each library only when an exercise needs it. A drawing function belongs to its library, not necessarily to the core grammar.

03 · programming model

Object orientation and organization

Project documentation states that Kalimat provides object-oriented features. Classes and objects help group state and related operations, but details such as visibility, inheritance, and constructors should be checked in the rules document for the relevant version.

This organization can support exercises that progress from small functions to object models. A useful first step is to identify which values belong to each entity and which operations change those values before choosing a language construct.

Do not automatically transfer rules from Java, C++, or another object-oriented language. Kalimat’s model is defined by its own official documentation.

Plan a model before looking for syntax

To understand object orientation without assuming specific features, start with the problem: what entities exist, what data does each one hold, and which actions change that data? An activity about a shape, for example, can separate position, color, and drawing operations. Then look up how the current Kalimat guide represents each idea.

ConceptWhat to check in the guide
Type or classHow is a category of objects declared and named?
InstanceHow is a value created, and how are its fields initialized?
StateWhich data belongs to each object, and how can it change?
OperationHow does a method receive arguments and produce effects or results?

This is a reading guide, not a claim that every object-oriented feature matches Java or C++. Inheritance, visibility, constructors, and overloading should be used only when they appear explicitly in the Kalimat documentation.

04 · concurrent execution

Concurrency in the CSP model

Kalimat also advertises a concurrency model related to CSP (Communicating Sequential Processes). Rather than treating all work as one sequence, the model allows learners to reason about processes that execute and communicate.

  • Process: an execution unit with an identifiable task.
  • Communication: data exchange or synchronization between processes using language constructs.
  • Coordination: define when each process can continue and how results are combined.

Concurrency requires attention to order and synchronization. Consult the official guide before using particular terminology or communication forms; this page does not specify CSP operators absent from the sources summarized here.

Reasoning about processes and communication

The CSP label points to reasoning about sequential processes that communicate. Before looking for syntax, describe each process as a task and identify the data or event that lets information pass between them. A conceptual exercise could have one process produce values and another draw each value it receives.

Check three conditions while planning this kind of solution:

  • which process produces each item of data and which one consumes it;
  • where communication synchronizes the two sides;
  • what happens if one process ends first or does not produce a value.

This planning avoids treating concurrency as simply “running two lines at once.” The names of operators, channels, processes, and synchronization instructions must come from the installed grammar; this page does not translate or reconstruct them.

05 · libraries

2D graphics and games

The project highlights a 2D graphics library for building scenes and games. This feature connects programming concepts to visible outcomes: drawing objects, responding to events, and updating a scene.

A learning sequence can start with a window and a simple shape, then introduce movement and interaction. For each exercise, identify:

  1. which objects appear on screen;
  2. which properties change between updates;
  3. which events trigger an action;
  4. which rules keep the scene within desired bounds.

Module, function, and event names depend on the API distributed with Kalimat. Use the examples shipped with the package to confirm exact calls.

From a first shape to a small game

Study the graphics library in stages that keep a program easy to check. Begin with a static shape; then change one property, such as position or color; only then connect updates to an event or a sequence of frames if the version's materials document that feature.

  1. Find how an official example creates a window or drawing surface.
  2. Identify the arguments needed for a simple shape.
  3. Change one argument and observe only that visual difference.
  4. Read how the library receives input and updates a scene.
  5. Separate the game's rule from its visual presentation into testable parts.

This is a way to study a 2D graphics library, not a list of exact API names. Use the package examples to confirm events, coordinates, units, colors, and the update cycle.

06 · interoperability

Integrating with C

The official portal also documents interoperability with C. This bridge can provide access to native code or libraries where appropriate, but it crosses type and resource-management models that need to agree.

Before calling external code, confirm:

  • how types on each side are represented;
  • who allocates and releases each resource;
  • how errors and return values are communicated;
  • which conventions and header files the tool requires.

Interoperability is an advanced topic and is not needed for first programs. A native library must be compatible with the version and platform in use.

A careful boundary between languages

Interoperability with C is an advanced feature. Before connecting a routine, write down the contract on both sides: argument names and order, accepted types, result, possible errors, and who releases memory. The package documentation should explain how a function is found and how its types are represented.

QuestionWhy check
Do the types match?An incorrect conversion can corrupt values or memory.
Who owns the resource?Both languages must agree on allocation and release.
How are errors returned?A failure must be detected without leaving inconsistent state.
Which environment is supported?Compiled libraries and calling conventions vary by platform.

Start with the smallest example supplied with the distribution. Do not treat an FFI example as a requirement for every Kalimat program.

07 · syntax and features

Finding the grammar

The project distributes language rule documents and examples with its installation files. Those documents are the appropriate source for checking keywords, punctuation, declarations, expressions, classes, processes, and graphics APIs.

Because the public page consulted does not expose a complete, stable grammar as plain text, this reference does not reconstruct a “Hello, world” example. To get a verifiable program:

  1. download a release from the official portal;
  2. open the language rules documents included in the package;
  3. run one of the provided examples first;
  4. change one part of the example and compare the result.

This avoids assigning Kalimat syntax guessed from a description written in another language.

What comes with the official package

The official getting-started guide recommends downloading the distribution, extracting it, and launching its included executable. The package contains two PDF documents: a short rules summary and a longer guide. It also includes simple and complete example folders. These are the best sources for checking the grammar of that release and trying programs without reconstructing syntax from a project description.

Beginners can follow the introductory course linked by the project; experienced programmers can start with the short PDF and consult the detailed reference when a new construct appears. The official page currently labels a distribution dated May 3, 2025; check the version label on the portal before comparing examples.

How to read an example without mixing versions

  • Record the version and system used by the material.
  • Run the example unchanged and save its output.
  • Change one declaration or expression and compare the result.
  • Use the detailed PDF to confirm the rule behind the change.
  • Do not copy reserved words from one Arabic programming language into another.

08 · study and debugging

A learning path

Start with official examples and identify the required runtime. Then move from text output to variables, conditions, loops, and functions. Introduce objects, concurrency, graphics, or native integration only when an exercise calls for those features.

  • Keep the package version with the examples you test.
  • Change one thing at a time, especially in Arabic writing and text direction.
  • In a visual program, validate the logic before adding extra events.
  • For concurrency, test different orders and inspect synchronization points.
  • For C interoperability, begin with a minimal project example.

Materials and implementation choices can evolve; check the guides shipped with the installed version.

A sequence of exercises with checkpoints

A short progression helps separate language features from library features:

  1. run a minimal example included in the distribution;
  2. change an input and predict the result before running it;
  3. find the rule used by the example in the manual;
  4. study a program organized around objects or functions if the guide presents that form;
  5. choose a graphics, concurrency, or interoperability task only after understanding its prerequisites.

When an error appears, keep the complete message, note the version, and reduce the program to the smallest part that still fails. This record helps distinguish a syntax error from a library or environment configuration problem.

09 · versions and scope

What this reference covers

The features described here—Arabic-language programming, object orientation, a CSP model, 2D graphics, and C interoperability—are those advertised by the official project consulted. This page does not attempt to fix every syntax detail or claim compatibility between versions.

The official distribution includes rules and examples that should be used to verify the grammar and runtime. Kalimat remains under evaluation for Potoo IDE; nothing on this page should be read as an implemented integration.
